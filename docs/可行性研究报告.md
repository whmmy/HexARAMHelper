# HexARAMHelper 可行性研究报告

> 海克斯大乱斗 AI 辅助工具：英雄出装推荐 + 海克斯推荐 + 基于战局的克制/加强决策
> 日期：2026-09-24 | 参考项目：`E:\project\lol-aram-mayhem-hextech-helper`

---

## TL;DR 结论

**可行，且比预想的更可行。** 三个核心判断：

1. **"根据战局克制对面"所需的数据，游戏自己就会告诉你，不需要任何 OCR 猜测。** League 本地有两个官方只读 API（LCU API 和 Live Client Data API），能拿到：双方 10 人阵容（加载期就绪）、敌方每个人的实时出装/KDA/金币（游戏内秒级轮询）。参考项目其实已经在调这些 API 了，只是只用它取了自己玩的英雄。

2. **Jev 不是必须的，你提的替代方案（聪明模型全盘分析 + 小模型快速给意见）成立，且就是推荐形态。** 因为所有决策窗口都是"人拍板"级别（海克斯选择约 30 秒倒计时、出装完全不限时），1~3 秒的 flash 级小模型完全够快。Jev 的亚秒级响应在本项目里是优化项，不是门槛。

3. **参考项目约 60% 的代码可直接复用**（LCU 连接、OCR 识别、悬浮窗、爬虫框架、胜率数据库），新工具的增量主要在：读双方阵容、读敌方出装、出装数据库、规则引擎、两层 AI 接入。

## 1. 参考项目资产盘点

参考项目（Python + Tkinter + RapidOCR）目前的推荐逻辑是纯查表：OCR 认出屏幕上 3 个海克斯 → 查 OP.GG 爬来的胜率 CSV → 按总排名排序高亮。没有任何局势推理。

| 组件 | 文件 | 复用性 | 说明 |
|---|---|---|---|
| LCU 连接器 | `scripts/lcu_connector.py` | ★ 直接复用+扩展 | 三段式取英雄（ChampSelect → GameFlow → Live API）已实现。**关键：`get_gameflow_champion()` 已经在遍历 `teamOne + teamTwo`，取敌方 5 人只需去掉"只匹配自己 summonerId"的过滤，几行改动** |
| OCR 识别 | `main.py` GameAnalyzer | ★ 直接复用 | 截 3 个海克斯标题区域 → RapidOCR（毫秒级）→ thefuzz 模糊匹配（>60 分），已解决分辨率自适应和识别率 |
| 悬浮窗 | `main.py` OverlayApp | ★ 直接复用 | Tkinter 透明置顶鼠标穿透遮罩，F6/F7/F8 热键闭环 |
| 数据管道 | `scripts/hero_scraper.py` | ★ 复用模式 | Selenium 爬 `op.gg/zh-cn/lol/modes/aram-mayhem/{英雄}/augments`，含 ChromeDriver 缓存/兜底逻辑；扩展爬出装用同一套 |
| 胜率数据库 | `data/hero_augments.csv` | ★ 直接复用 | 31,133 行：英雄 × 海克斯 × 等级(白银/黄金/棱彩) × 总排名。作为推荐先验 |
| GitHub 数据兜底 | `scripts/updater.py` | ★ 直接复用 | 本地无 Chrome / 网络受限时的数据更新通道 |

一个有意思的细节：CSV 里大量 `升级：死亡之舞`、`升级：焚天` 这类**装备升级型海克斯**——海克斯选择和出装路线是互相影响的，这正好支撑"出装 + 海克斯必须一张统一作战方针里出"的架构设计（见 §3）。

## 3. 推荐架构：三层设计

```
┌─ 层0 确定性层（无 AI，常驻） ─────────────────────────────┐
│  LCU + Live API 轮询 → 战局快照（双方阵容/敌方出装/KDA/金币）│
│  OCR 海克斯三选一 → 胜率先验（CSV 查表）                     │
│  规则引擎 v1：敌方 AP 占比>60%→魔抗权重↑；治疗型英雄≥2→减疗； │
│  敌方 poke/突进阵容类型识别 → 对应出装提示                    │
└──────────────────────────────────────────────────┘
            ↓ 战局快照
┌─ 层1 System 2：聪明大模型（低频，每局 1~2 次） ─────────────┐
│  触发：加载界面双方阵容就绪时（30~60s 窗口，用得起大模型）     │
│  输入：双方阵容 + 我的英雄 + 出装/海克斯数据库 + 知识标签库    │
│  输出（结构化 JSON，缓存整局）：                              │
│    · 敌我阵容分析（伤害构成、开团/poke/后期类型、威胁位）      │
│    · 本局出装路线（核心 3 件 + 分支条件：如"敌 3AP 则第 4 件换 X"）│
│    · 海克斯优先级表（带一句话理由，供层2引用）                │
│  战局突变（如敌方某人起飞/换装）→ 手动/自动触发增量刷新        │
└──────────────────────────────────────────────────┘
            ↓ 整局方针（缓存）
┌─ 层2 System 1：快速裁决（高频，每次海克斯/出装决策 1 次） ───┐
│  输入：3 个候选海克斯 + 层0 战局快照 + 层1 方针 + 已选海克斯   │
│  输出：三选一排序 + 理由                                      │
│  实现可插拔（同一 DecisionEngine 接口）：                     │
│    A. flash 级小模型（GLM-4-Flash / Qwen-Flash / Gemini Flash）│
│       1~3s，自带文本理由，生态成熟 ← 推荐首发                 │
│    B. Jev Choice 原语：0.1~0.5s，校准概率，零幻觉            │
│       但不生成文本 → 理由需引用层1的预生成模板                 │
└──────────────────────────────────────────────────┘

最终分数 = 胜率先验（层0，确定性）+ 语境修正（层2）
任何一层挂掉都有下层兜底 → 网络断了退化为参考项目的纯查表模式
```

要点：
- **System 2 的"全盘分析"每局只做一次并缓存**，不要每次决策都现想——这是延迟和成本都能压住的关键。
- **胜率先验和 AI 修正分离**：AI 说错了顶多影响排序微调，底座始终是 OP.GG 真实胜率，鲁棒且可解释。
- 出装推荐天然分流：核心装跟 System 2 路线走（不限时），第 4~6 件在回城/死亡时按实时敌方出装从"分支条件"里挑。

## 4. Jev 是什么，以及它是否必须

### 4.1 Jev 背景（2026-09-15 开放早期访问，最近爆火）

TypeSafe AI（前 OpenAI 研究员创立）推出的首个「系统一模型 / 结构化评估模型」：

- **不生成文本**。输入程序状态（文本/JSON）+ 一组类型化问题，输出三种原语：**Choice（选项）、Score（评分）、Noul（无答案）**，每项带**校准概率**。
- **快**：端到端 70~500ms，约为前沿 LLM 同任务的 200 倍，可持续 ~10 次/秒决策。
- **便宜**：比传统 LLM 低数十倍；**零幻觉**（封闭选项判断，不存在编造）。
- 社区玩法：游戏实时控制（Doom）、路由/分类、LLM-as-judge 裁决、检索重排等。

### 4.2 映射到本项目

海克斯三选一**字面上就是 Jev 的 Choice 原语**（3 个候选 + 语境 → 选择 + 概率），装备打分就是 Score。契合度确实高。

### 4.3 但是——时延预算表说明它不是门槛

| 决策场景 | 实际可用时间 | flash 小模型 (1~3s) | Jev (0.1~0.5s) | 前沿大模型 (5~20s) |
|---|---|---|---|---|
| 加载期全盘分析 | 30~60s | 不适合（太浅） | 不适合（不做生成） | ✅ 正好 |
| 海克斯三选一 | ~30s 倒计时，且由你手动点 | ✅ 无感 | ✅ 秒回 | ⚠️ 勉强可行 |
| 出装调整 | 回城/死亡时，不限时 | ✅ | ✅ | ✅ |
| 连续评估（如每 2s 重估装备优先级） | 秒级 | ⚠️ 费且慢 | ✅ 唯一合适 | ❌ |

**没有任何一个 v1 场景硬性要求亚秒响应。** 决策最终都是你人手点的，1~3 秒出建议在体验上无感。所以：

> **结论：Jev 非必须。你的直觉（"聪明的做全盘搜索 + 小模型快速给意见"）就是这个项目的正确形态**——聪明的全盘搜索 = System 2 每局一次；小模型快速意见 = flash 级 LLM 足矣，还白送自然语言理由（Jev 不写理由，得靠层 1 预生成模板兜）。

### 4.4 Jev 什么时候值得接

作为**可插拔后端**（`DecisionEngine` 接口之下的第二个实现），在以下情况升级价值明显：
1. 想做**连续评估**玩法：比如每隔几秒根据敌方新出的装备重估你的第 5/6 件优先级、实时提示"该补魔抗了"——10 次/秒 + 极低单价只有它扛得住。
2. 想要**校准概率**做自动化阈值：高置信直接自动高亮，低置信才打扰你。
3. 调用量涨起来后成本敏感。

风险对冲：Jev 还是 early access，生态新；接口抽象后随时可切回 flash LLM，零返工。

## 5. 方案对比

| 方案 | 推荐质量 | 延迟 | 成本/局 | 复杂度 | 离线可用 |
|---|---|---|---|---|---|
| A. 纯规则增强版（参考项目 + 阵容/装备规则） | ★★★（能处理 80% 常见克制） | 0 | 0 | 低 | ✅ |
| B. Jev 中心（Jev 做所有决策） | ★★★（缺全盘分析能力） | 极低 | 极低 | 中 | ❌ |
| C. **System2 大模型 + flash 小模型（推荐）** | ★★★★★ | 无感 | <¥0.1 | 中 | 规则兜底 ✅ |
| D. 单一大模型每次现算 | ★★★★（无缓存一致性） | 海克斯场景偏慢 | ~¥0.1~0.5 | 低 | ❌ |

成本估算（方案 C）：每局 ≈ 1 次大分析（~10k tokens）+ 6 轮海克斯裁决 + 3 次出装刷新 ≈ 十来次小调用 + 一次大调用。flash 级价格下每局不到一毛钱，免费额度大概率直接覆盖。（报道中"Jev 玩 1 小时 $7"是 10 次/秒连续控制场景，与本项目每局十次的事件驱动量级完全不同。）

## 6. 风险与合规

| 风险 | 等级 | 对策 |
|---|---|---|
| Riot 第三方政策 | 低~中 | 只读本地 API + 不代操作游戏 ✅（与 Blitz/Porofessor 同类）。但注意：开发者政策明确**禁止展示 Augments / Arena 道具的胜率**（写在 Live Client Data API 文档页）。对策：胜率先验展示保持走 OP.GG 抓取源（参考项目现状，不走 Riot API）；Live API 只取战局事实（阵容/出装/KDA）——两源分层不混用即可站得住。个人自用风险极低，若分发需严守此界 |
| OP.GG 模式页随轮换下线 | 中 | 数据快照入库 + GitHub 兜底（参考项目已有此机制），模式回归时增量更新 |
| Live Client Data API 在大乱斗变体的字段行为未实测 | 低 | P0 第一天实测验证（官方文档标准字段，ARAM 系模式历史可用） |
| OCR 误识别 | 低 | 参考项目模糊匹配已解决；识别失败时退化为手动输入海克斯名 |
| Jev 供应/变动 | 低 | 已用接口抽象规避，flash LLM 为主实现 |
| 已选海克斯记账不准 | 低 | v1 用"每轮识别 + 推荐/确认记录"，后续可 OCR 记分板增强 |

### 6.1 合规详解（2026-09-24 补充，含政策原文）

Riot 对工具的约束实际是**三层独立的东西**，很多人混在一起谈：

**第一层：Riot 开发者政策（条款层面）。** 关键原文（摘自 developer.riotgames.com 的 Developer Policy / Live Client Data API 文档页）：

> "Products cannot display win rates for Augments or Arena Mode items. **This applies to all websites, applications and overlays.**"（禁止展示海克斯/Arena 道具胜率，适用于所有网站、应用和悬浮窗）

> "Products may not provide any game-session-specific information that would be previously unknown." / 产品不得使用客户端中不存在的信息给予竞争优势（例：自动追踪敌方大招 CD）

> "Apps that **dictate** player decisions."（禁止"代替"玩家做决定的产品）

**修正一个早前判断**：胜率禁令原文写明"applies to all websites, applications and overlays"——不限数据来源，理论上 OP.GG 爬来的胜率也在内（参考项目严格读同样落在这条里；它能公开存在说明执行层面针对的是注册产品/公开分发/变现产品，而非个人本地工具）。因此对策升级为：**展示层只输出推荐档位（S/A/B）+ 理由，不展示胜率数字**——我们的最终分数本来就是"先验+语境修正"的合成排序，去掉百分号成本为零。

**第二层：Vanguard 反作弊（技术层面）。** 只查进程注入、内存读取、输入模拟、内核驱动。本工具的技术栈 = 只读本地 HTTP（游戏主动暴露的端口）+ 屏幕截图 OCR + 透明悬浮窗，与 Riot 容忍的 Blitz/Porofessor/OP.GG 桌面端完全同型，不触碰 Vanguard 红线。**绝对红线：不向游戏注入任何输入（不做自动买装/自动选海克斯点击），悬浮窗鼠标穿透只显示。**

**第三层：数据源法务。** OP.GG 爬取违反其站点 ToS 的风险是 IP 封锁/验证码（工程问题），个人自用无实质法律暴露；参考项目已带 GitHub 镜像兜底。若将来分发，可切换为 Riot 官方 API 自采数据（需注册 + 守第一层条款）。

**逐条对照本项目：**

| 我们做的事 | 政策条款 | 结论 |
|---|---|---|
| 读双方阵容/敌方出装/KDA（Live API） | "不得使用客户端不存在的信息" | ✅ 全是玩家可见信息（加载界面、TAB），只是聚合展示 |
| 悬浮窗显示出装/海克斯推荐 | "dictate player decisions" | ✅ 是建议不是代操作，人手点击；Blitz 出装悬浮同性质 |
| 显示海克斯推荐排序 | 胜率展示禁令 | ⚠️ 展示档位而非胜率数字即绕开；个人自用无执行风险 |
| OCR 识别屏幕 | — | ✅ 屏幕内容本就可见 |
| 不注册开发者门户 | "面向玩家的产品须注册" | ✅ 个人自用非"player-facing"；分发时才需注册 |

**底线结论：个人自用——三层全不踩，零实质风险，放心做。公开分发——需要：注册 + 去胜率数字展示 + 保持不代操作 + 免责声明（"未经 Riot 认可"）。**

P0+P1 不依赖任何 AI，先跑通数据闭环、验证价值；AI 是在其上的增强，随时可加。
