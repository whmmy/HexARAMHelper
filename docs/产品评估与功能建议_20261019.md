# 产品评估与功能建议（PM 视角，2026-10-19）

> 本文以产品经理视角盘点 HexARAMHelper 现状：已验证的能力、真实缺陷、建议的新功能与落地顺序。
> **全部结论基于仓库内实证数据**（探针落库 1.58MB、真实对局复盘 10 局、AI 调用台账 162 条），
> 不引用推测；每条缺陷均带 `文件:行号` 或统计证据，可直接转成开发任务。
>
> 本文不改变 AGENTS.md 任何既定理念；所有建议均与「数据出事实，模型出判断」铁律兼容——
> 涉及判断的一律走模型权限扩张，涉及事实的一律走代码/数据侧。

---

## 1. 结论速览

**这是一个已经跑通、可以日常使用的工具**，不是原型：

- 近 10 局真实对局**全部** `mode=ai / ctx=ai`，无一局降级到规则模式；
- 海克斯记账 10/10 局成功（每局 4~6 个）；
- 单局 AI 成本 ¥0.032~0.087，中位 **¥0.062**；
- 三层架构、规则兜底、防幻觉校验、复盘落盘、上局回顾面板均已实装。

**但产品的"复盘"与"判断质量"两处存在结构性缺陷**，而这两处恰好是产品承诺的核心
（"翻译成这局该怎么出装/选海克斯" + "上局回顾"）。修复它们不需要新数据、不需要新模型、
不需要新架构——需要的是**把已有的信息分层、去重、显性化**。

**最高优先级的 3 件事**：

| # | 事项 | 一句话 | 证据 |
|---|---|---|---|
| 1 | **海克斯阶级（棱彩/黄金/白银）全链路缺失** | 台账 43/43 条品质为空，因为记账时压根没传 tier；而 tier 数据已在 KB 里躺着 | `app.py:562` / `kb.py:229-232` |
| 2 | **最有价值的两类决策没进复盘** | 10 局 history 的 kind 全集只有 `{next_items, swap_items, event_note}`——出门装三选和海克斯三选一条都没留下 | `game_state.py:1231` |
| 3 | **AI 调用是设计值的 4 倍，因为建议 96% 是重复** | 中位 44.5 次/局（设计 8~11）；三选项的理由一字不差 | 10 局复盘 + 162 条调用台账 |

## 2. 已验证的产品能力（不用重做）

| 能力 | 状态 | 证据 |
|---|---|---|
| 三层架构（System2 预生成 / System1 局内 / 规则兜底） | ✅ 稳定 | 10/10 局 `ctx_source=ai` |
| 海克斯 OCR 记账 + 点击观察 | ✅ 稳定 | 10 局每局 4~6 个海克斯全记上，tier 除外 |
| Live API 敌我感知 | ✅ 稳定 | 威胁画像正常输出（如「法伤×2 \| 物伤×3 \| 治疗:血港鬼影 \| 关键装:莫雷洛秘典」） |
| 满装替换建议 | ✅ 稳定 | 10 局中 6 局触发 `swap_items` |
| 复盘 JSON 落盘 + 上局回顾面板 | ⚠️ 落盘正常，**内容被挤爆** | 见 §3.2 |
| 数据管线（OP.GG builds） | ✅ 新鲜 | `data/builds/` 更新至 2026-10-15 |
| 合规红线（不注入输入、不显胜率） | ✅ 守住 | overlay 只显 S/A/B 档 + 理由 |

**成本模型是健康的**：¥0.062/局、每天 10 把 ≈ ¥0.62，AGENTS.md 里"分级单价下成本可忽略"
的判断成立。即使把调用数砍到 1/4，节省也只有 ¥0.04/局——**所以下面的优化目标不是省钱，
是提质量和降噪。**

## 3. 不足（按严重度排序，每条可转任务）

### 3.1 P0-1｜海克斯阶级全链路缺失——玩家最在意的信息是空的

**事实**：
- `app.py:562` 记账调用是 `session.record_augment(name, card_idx=idx, round_id=rid)`，
  **没有传 tier**；tier 只在 `app.py:865`（mock）和 `tests/smoke_offline.py` 里出现过。
- 实证：近 10 局共 43 条海克斯台账，`tier` 字段 **43/43 为空**。
- 复盘 JSON 里同样是空串（`game_state.py:1364-1366` 写的是「tier 快照缺省为空串，UI 省略括号」）。

**但数据已经在库里了**：
- `kb.py:44` 的结构就是 `hero -> {augment_name: {tier, overall_rank, t_rank}}`；
- `kb.py:229-232` 从 `data/hero_augments.csv` 读取「等级」列（值域：棱彩/黄金/白银）与档内位次；
- CSV 共 31,133 行，**无 `???` 占位行**（竞品报告 §3.3 提到的占位问题已不存在）。

**影响（三层）**：
1. **UI**：overlay 台账的「（棱彩）」括号永远不显示；
2. **模型**：System1 拿不到「你抽到的是棱彩升级」这个事实，无法据此调整路线——棱彩在
   海克斯大乱斗里意味着额外多选一张，是本模式最值钱的事件；
3. **复盘**：无法回溯"哪一把抽到了棱彩"，也就无法做「抽到棱彩的局胜率是否更高」的分析。

**方案（两条腿，缺一不可）**：
- **A. OCR 阶级识别**：借鉴 PotatoHex 的 HSV 色块采样卡顶条判棱彩/黄金/白银
  （竞品报告 §5-P0-2 已给路径）。这是**硬事实，归代码**，符合理念 1。
- **B. KB 先验兜底**：`kb.augment_prior_rank(hero, name)` 已返回 `(档位, 档内位次)`，
  查表即可填 tier。但要**标注来源**（OCR 实抽 vs 先验推定）——同一海克斯在不同英雄的 CSV 行
  可能给出不同档位，且 reroll 会换卡，先验不等于实抽。
- **展示**：台账行加阶级徽章 + 轮次序号（①/②/③），复盘 JSON 一并带上。

### 3.2 P0-2｜复盘功能名存实亡——最有价值的两类决策被挤掉了

**事实**：
- `game_state.py:1231` 写盘时硬截 `self.history[-60:]`；
- `history.append` 只在三处：`game_state.py:890`（`_set_suggestion`）、`:999` / `:1018`（event_note）；
- `KIND_RANKS`（海克斯三选档位）分支在 `:920`，**不写 history**；
- `KIND_OPENING`（出门装三选）在 `:931` 是**原地改写** `cur.candidates`，不追加新条目。

**实证**：近 10 局 history 的 kind 全集 = `{next_items, swap_items, event_note}`。
**`opening` 与 `card_ranks` 一条都没有**。且每局 history 前 3 条**全部**是 `next_items`——
出门装三选即使写进去，也必然被 60 条高频 `next_items` 挤出去。

**影响**：产品给玩家做了「上局回顾」面板，但回顾不了：
- 出门装当时推荐了哪三件、玩家有没有听；
- 每一轮海克斯三选给了什么档位、玩家选了哪张、听没听。

**这恰恰是"版本翻译器"最核心的两个决策点**——恰恰是玩家最想知道"我为什么该听它的"。
而占满窗口的 `next_items`（下一件买什么）是复盘里信息价值最低的那一类。

**本质问题**：**日志被高频低价值事件淹没，缺少按类型的分层保留。**

### 3.3 P0-3｜建议重复率极高，AI 调用是设计值的 4 倍

**事实**：
- AI 调用数：近 10 局 `[44, 38, 51, 37, 55, 37, 52, 57, 45, 27]`，中位 **44.5**。
  实施计划 v4.2 的设计是「每局 8~11 次，硬上限 15」，当前 `budget_per_game=0`（不限）。
- 60 条建议里 54~60 条是 `next_items`（同一段出装主线反复刷新，只金币数变）。
- **三选项的理由没有区分度**。牛头酋长局连续 5 条 `swap_items` 里，
  ①②③ 的理由一字不差：「敌方物伤成型而它零护甲，换入补护甲短板」——只是装备名不同。

**机制**：`AGENTS.md` 记载触发模型是「定时快照 diff + 事件触发」，签名含
「金币档 250G 粒度」。一局金币从 0 涨到 ~20000，签名最多变 80 次 → 每次都重问模型。
`min_interval=20s` 守门只约束了 periodic 通道，**没有约束签名 diff 的粒度**。

**影响**：
- 成本浪费（虽绝对值不高，但问的是重复问题）；
- **质量下降**：模型没有被要求区分三条候选的理由，于是三条挤出一个理由；
- 复盘被淹没（与 3.2 同一根因）；
- overlay 视觉上是"同一句话一直在闪"。

### 3.4 P1-4｜时间线被 `click_dropped` 淹没

**事实**：牛头酋长局 timeline 200 条里，**128 条（64%）是 `click_dropped`**：
```
click_dropped | no_hex_evidence (1214,672) 卡2 矩形命中但无海克斯证据（界面刚关 >10s？）
click_dropped | reroll_no_evidence (1245,995) 刷新按钮命中但无海克斯证据
```
**影响**：
- 真正的里程碑（`augment_recorded` 1 条、`my_death` 5 条、`enemy_key_item` 1 条）被 200 条上限挤出；
- **这 128 次本身是产品缺陷信号**：点击观察器在卡片矩形命中了，但没匹配到海克斯证据 → 没记账。
  说明「点击位置」比「OCR 文本」更早更准，两者没对齐，存在**漏记账**风险（少一条海克斯 = 路线推断少一个输入）。

### 3.5 P1-5｜复盘缺"结果"维度，产品没有自我验证闭环

复盘 JSON 现有字段：hero / duration_s / ally / enemy / augments / final_items / current_path /
threat / engine / suggestions / timeline。

**缺**：胜负结果、KDA、召唤师名、装备变更时刻（只有终态）。
Live API 拿得到 KDA（overlay 已在用），补进去成本低。

**影响**：无法回答「这个助手到底有没有帮到我赢」。改进了建议质量，但没有任何指标能证明改进有效——
**产品失去了自我验证能力**，后续所有优化都只能靠感觉。

### 3.6 P1-6｜数据资产断链：海克斯先验既过期又无上游脚本

- `data/hero_augments.csv`（1.5MB / 31,133 行）最后修改 **2026-09-25**，距今 3 周；
  而 `data/builds/` 更新到 2026-10-15。**海克斯先验是全项目最旧的数据资产。**
- `scripts/` 下**没有生成它的脚本**（只有 `gen_champ_profile` / `fetch_opgg_builds` /
  `build_kb_tagger` / `reconcile_items`）——竞品报告 §3.3 指出的断链依然存在。
- 讽刺的是：§3.1 要用的 tier 数据正来自这个断链的文件。**它一旦不更新，3.1 的方案 B 就是在用过期答案。**

### 3.7 P2-7｜工程债（竞品报告已列，仍未做）

| 项 | 竞品做法 | 本项目现状 |
|---|---|---|
| overlay 防遮挡 | PotatoHex 每 1s 重申 topmost | 只在创建时设一次（`overlay.py:75` 注释自承） |
| overlay 重绘 | 签名去重防重绘 | 500ms 全量刷，可去闪烁 |
| LCU 轮询 | 互斥 + 指数退避重连 | 无 |
| 分发形态 | launcher 自装依赖 | 源码运行 + 杀软误报预案 |

注：按 AGENTS.md「个人自用边界」定位，分发体系**不建议投入**，只做前两项低风险工程债。

### 3.8 结构性约束澄清｜敌方海克斯：API 直读已被真机证伪

竞品报告 §1 的 P0-1「海克斯可从 API 直读」——**在本模式不成立**：

| 指标 | 数值 |
|---|---|
| 探针落库总行数 | 1,576 |
| 覆盖对局 | 3 局（session 1~3） |
| 玩家·帧总数 | **15,760** |
| 其中 `runes` 字段 present | **0** |
| absent | 15,760（100%） |

`log/runes_probe/runes_probe.jsonl` 逐帧记录 `allgamedata`（1,900 玩家·帧）与
`playerlist`（13,860 玩家·帧）的 `runes` 容器，**一次都没出现过**。

**三个结论**：
1. AGENTS.md「敌方海克斯识别暂缓（API 读不到）」的既定结论**现在有了硬证据**，不用再猜；
2. 竞品报告的 P0-1 可以关掉了，**省下一整轮工程**；
3. 敌方海克斯**只能间接推断**。而且注意：敌方的海克斯界面在屏幕外，
   **靠 OCR 识别敌方海克斯在物理上就不可行**——不要在这条路上投工程。

> 另：`experiments/summarize_runes_probe.py` 已在库，探针本身是只读旁路、不进推荐链，
> 保持现状即可（它现在是一份长期有效性证据）。

### 3.9 敌我信息不对称｜现状是死规则，机会在模型

敌方海克斯读不到，但**敌方出装读得到**。目前只用 `KEY_ENEMY_ITEMS` 这类**硬编码语义表**
做「敌方出了莫雷洛秘典 → 提示重伤」。

对照铁律 1（模型有自主权，代码不做语义裁判）与铁律 4（数据直出，模型出判断）：
**这正是应该交给模型的地方**——把敌方阵容 + 敌方出装 + KDA + 死亡来源**原样喂给模型**，
让它自己判断「对面这个莫雷洛说明他拿了什么海克斯、对我意味着什么」，而不是继续往
`KEY_ENEMY_ITEMS` 里加条目。这既符合既定理念，也是本模式敌方信息榨取的上限。

## 4. 建议的新功能

### N1（P0）海克斯阶级识别 + 台账增强 → 补上"最值钱信息"

- **双通道**：OCR HSV 色块识别实抽阶级（代码判事实）+ KB 先验兜底（标注来源）
- **UI**：台账行显示「① 棱彩 · 升级：无尽之刃」；overlay 与复盘同步
- **模型**：阶级进 System1 上下文（"已选【棱彩】升级：无尽之刃"），让模型自己判断是否改路线
- **数据**：KB 侧补 `augment_tier(hero, name)` 直查接口，复用已有 `augment_prior_rank`

### N2（P0）建议历史分层保留 → "决策账"与"刷新流"分离

把 `history` 从单一流水线改成**按 kind 分桶**：

| 桶 | 成员 | 配额 | 理由 |
|---|---|---|---|
| 决策类 | `opening` / `card_ranks` / `swap_items` / `event_note` | 全量保留（每局几十条量级） | 低频高价值，是复盘的主体 |
| 刷新类 | `next_items` | 只留**结论变化**的快照 | 高频低价值，是噪音源 |

"结论变化"的判定 = 候选集合变化 or 理由变化 or 顺序变化；**纯金币数字变化不存**。

**这一条同时解掉 §3.2 和 §3.3 的数据侧问题**——重复被自然消掉，且不需要动触发逻辑。

### N3（P0）结论指纹去重 → 同一事实不重复问

给每条建议算指纹（候选名集合 + 归一化理由 + 档位）：
- 指纹不变 → **不更新 overlay、不写 history、不重派 AI**；
- 例外：可买性/差价发生变化（金币档跨档）时允许刷新，但同样要走指纹判定。

**性质**：这是**事实层去重**（同一事实不重复呈现/不重复问），不是语义裁判——不违反铁律 1。
**收益**：AI 调用 44 → ~12；overlay 不再闪；复盘有信号。与 N2 是同一件事的两面
（一个管「存什么」，一个管「什么时候产生」），建议**合并为一次改动**。

### N4（P1）复盘加"结果"与"命中率" → 建立产品自我验证闭环

**落盘补字段**：胜负、KDA、召唤师名、装备变更时刻（不只是终态）。

**新增「本局账本」一屏**（主窗口复盘区升级）：

| 维度 | 展示 | 回答的问题 |
|---|---|---|
| 出门装 | 推荐 A/B/C，玩家买了哪个 | 听劝率 |
| 每轮海克斯 | 给了三档，玩家选哪张 | 海克斯建议的采纳率 |
| 出装主线 | 建议 N 次，采纳 M 次 | 装备建议的采纳率 |
| 结果 | 胜负 + KDA + 分均 | 这把赚没赚 |

**这是把"我觉得有用"变成"数据显示有用"的唯一路径**。没有它，§3.3 那类质量优化无法验证。

### N5（P1）敌方画像模型化 → 用模型榨干间接情报

- 现状：`KEY_ENEMY_ITEMS` 硬表（只覆盖莫雷洛等少数几件）
- 建议：敌方阵容 + 出装 + KDA + 死亡来源**原样喂 System2/System1**，
  由模型判断「对面这个出装组合暗示他拿了什么海克斯、威胁在哪」
- **红线**：不新增任何"哪件装备=哪个海克斯"的语义名单；不触发额外 LLM 频次
  （复用既有调用，把敌方信息并入现有 prompt）
- 收益：在敌方海克斯物理不可读的前提下，把间接证据用到极限

### N6（P1）数据流水线补齐 → 修断链

- 新增 `scripts/fetch_hero_augments.py`，与 `fetch_opgg_builds` 同为天级刷新
- 设置面板的"数据新鲜度"把 `hero_augments` 纳入监控（当前只管 builds）
- **必须先于 N1 落地**，否则 N1 的兜底通道用的是三周前的答案

### N7（P2）选人期价值前置

现状：选人期只用来后台预生成 ChampionContext，**对玩家完全不可见**。
竞品 hex-helper 有"队友/板凳英雄排序"、PotatoHex 有 `championPickIntent`。

**机会**：选人期就让 overlay 给出「我这把的定位（输出/坦克/前排）」+「对面阵容的应对方向」，
把情报价值从"开局后"提前到"选人时"——这是玩家最需要信息、也最有时间吸收信息的时刻。
**注意**：必须保持零输入（不选流派、不点路线），纯展示，符合理念 6。

### N8（P2）overlay 与轮询工程债

1s topmost keepalive（防无边框全屏盖住 overlay）→ 500ms 全量重绘改签名去重
→ LCU 指数退避重连。**低风险、纯收益**，可与主线并行。

## 5. 建议落地顺序

| 批次 | 内容 | 为什么这个顺序 |
|---|---|---|
| **第一批** | N2 + N3（分层保留 + 结论指纹去重） | 一次改动同时解 4 个问题：复盘可用、调用减半、overlay 不闪、历史有信号。不需要新数据/新模型，风险最低 |
| **第二批** | N1（阶级识别）+ N6（数据流水线） | 补上玩家最在意但现在没有的信息；同时修断链，保证 tier 来源不是过期答案 |
| **第三批** | N4（结果与命中率） | 建立自我验证闭环——**在第一批生效后立刻做**，才能量化第一批的效果 |
| **第四批** | N5（敌方画像模型化） | 扩模型权限、符合铁律；等底子干净了做效果更好 |
| **随时并行** | N8（overlay/轮询工程债） | 独立、低风险 |
| **观察后再定** | N7（选人期价值前置） | 需先确认选人期 overlay 的呈现密度不干扰选人操作 |
