# 竞品对比调研报告：PotatoHex / hex-helper / ARAM-tool（2026-09-30）

> **调研对象**：`E:\project\PotatoHex`、`E:\project\hex-helper`、`E:\project\ARAM-tool`，
> 并重审 `E:\project\HexARAMHelper`（本项目）当前状态。
> **调研方法**：4 个只读探索智能体并行深挖（三家竞品各一 + 本项目盘点一），
> 关键结论由人工读码复核（海克斯 API 探针证据链已逐行核实）。
> 全部结论附 `文件:行号` 证据。本文档为事实记录与融入建议，不改变
> AGENTS.md 任何既定理念。

## 1. TL;DR

三家竞品与本项目**同赛道**（海克斯大乱斗助手），但走「统计查询器」路线：
爬第三方统计站直显胜率/评级，无局内感知个性化。本项目三层架构
（System2 方案池 + System1 局内权衡 + 规则兜底）是四者中唯一的"个性化动态
推荐"实现，能力面不输。

**最重要的发现——海克斯可以从 API 读到**：ARAM-tool 用 Live Client Data
API 的 `allgamedata` 端点读到 `allPlayers[].runes.generalRunes[]`，其中
`id > 100000` 的条目就是已选海克斯（`ARAM-tool/lcu_client.py:640-665`），
且 LCU `/lol-perks/v1/perks` 可把 id 映射回名字
（`ARAM-tool/lcu_client.py:297-314`）。本项目既定结论"海克斯 API 读不到"
（敌方海克斯识别因此搁置）**至少对自家英雄是错的**——我们的
`live_api.py` 从未解析 runes/perks 字段。敌方是否同样暴露需真机验证，
若成立，"敌方海克斯暂缓"可以解封（已记入
[真机验证清单.md](真机验证清单.md) §6）。

其余吸收点：PotatoHex 的 OCR 稳定性套件与海克斯阶级色块识别、三家各自的
数据源与缓存策略、overlay 防遮挡 keepalive 等工程细节，见 §5。

| 成熟度 | 活跃开发，真机案例文化 | 可用个人工具（B 站作者） | 2.5 周冲刺后停更（26 commits） | AI 代写，1 个月后停更（60 commits） |

三家竞品共同点：都爬**第三方海克斯大乱斗统计站**（PotatoHex 旧版与
ARAM-tool 同爬 apexlol.info，疑似同源），都不做局内感知个性化——玩家拿到的
就是"该英雄所有海克斯的胜率排行榜"，实际抽到什么与推荐脱节。这正是本项目
"OCR 记账 + 方案池权衡"要解决的痛点。

## 3. 同一功能，四条实现路径

### 3.1 局内感知（拿到"现在发生什么"）

- **本项目**：Live Client Data API `https://127.0.0.1:2999` 轮询
  `/activeplayer`、`/playerlist`、`/eventdata` 三端点每 5s
  （`hexa/core/live_api.py:243-251`），拿装备/金币/KDA/死亡/击杀事件；
  LCU 仅 HTTPS REST（进程命令行+lockfile 双路凭证，
  `hexa/core/lcu.py:60-99`），PhaseMachine 2s 轮询 gameflow-phase 驱动阶段
  状态机（`lcu.py:346-441`）。
- **PotatoHex**：游戏内完全不走 API，`ImageGrab` 截图（EnumWindows 定位
  LoL 窗口 bbox，`hextech_core.py:1945-2028`）+ OCR；选人阶段走 LCU 三端点
  （gameflow-phase :1378 / champion-summary :1799 / champ-select session
  :1839），连悬停意向 `championPickIntent` 都读（:1859）。LCU 凭证用
  ctypes+ntdll 读客户端进程命令行（:1474-1537）。
- **hex-helper**：纯 LCU HTTPS，PowerShell `Get-CimInstance` 读
  LeagueClientUx.exe 命令行取凭证（`lcu-service.js:14,28-68`），3s 轮询
  仅 3 个 GET；游戏内零感知。
- **ARAM-tool**：LCU 全家桶（含 `/lol-perks/v1/perks` :303）+ 2999
  `allgamedata` 补充局内（:280），psutil 读进程命令行取凭证
  （`lcu_client.py:36-66`，注释明言兼容 WeGame 国服 lockfile 为空）。

### 3.2 海克斯识别（本项目核心难点）——四条路线

1. **本项目**：RapidOCR(onnxruntime) + thefuzz 72 阈值匹配 229 名单
   （`ocr_engine.py:25-36,70-90`）；待机 2s/活跃 1s/唤醒 0.5s 轮询 +
   模板预筛 + 迟滞确认（`screen_detect.py:389-391,657`）；点击即抓帧后台
   补扫记账（`app.py:139-182`）；reroll 强制重扫（:184-191）。
2. **PotatoHex**：Windows.Media.Ocr 经 powershell 子进程调用（每帧冷启
   进程，开销大，`hextech_core.py:2132-2186`）+ 2x 放大 + HSV 白字掩码/
   tophat+Otsu/CLAHE 自适应阈值多候选择优（:2302-2316）；左卡快速探针→
   三卡确认分级（:2380,2413）；候选短路（:2358-2373）；2.8s sticky 缓存抗
   单帧丢失（:2632-2650）；0.5s 节流（:122）；difflib 匹配阈值 0.52
   （:2675-2688）。**另用 HSV 色块采样卡片顶部条识别阶级（棱彩/黄金/
   白银）**（:2065-2129）。附带离线 ROI 调参工具（`test_ocr_roi.py:202-214`）
   与 OCR 调试 dump（:378-399）。
3. **ARAM-tool**：**走过本项目的路又砍了**——遗留 RapidOCR+cv2+difflib
   分级阈值代码（`apexlol_data.py:503-679`，与本项目同款技术选型），
   v2.5.0 删掉 OCR 中间层，直接把截图裁剪压缩喂 Gemini 多模态
   （`screenshot.py:12-47`，"砍掉不靠谱的 OCR 中间层" main.py:464）。
   代价：每次海克斯三选一都烧 LLM 调用（本项目预算 15/局吃不起）。
4. **API 直读（本次发现）**：Live API `runes.generalRunes` 的
   `id>100000` ——根本不需要 OCR，见 §1 与真机验证清单 §6。

### 3.3 版本数据获取

- **本项目**：OP.GG RSC flight 流直解（无需浏览器，
  `scripts/fetch_opgg_builds.py`）→ `data/builds/` 174 英雄 json

  海克斯先验 `hero_augments.csv` + `augments.json`（LLM 批量打标
  `build_kb_tagger.py`）。弱点：`hero_augments.csv` 有"？？？"占位行不入库
  （`kb.py:137-140`），且 `scripts/` 里没有生成它的上游脚本。
- **PotatoHex**：aramgg.com **四级解析回退**（RSC payload→HTML 表→
  __NEXT_DATA__→JSON-LD，`main.py:1168-1174`）——站方改版即失效的防御；
  缓存 JSON 带 schema 版本号，`parse_schema_version` 强制迁移重爬
  （`main.py:1305`）；TTL 分级（索引 12h/英雄详情 6h，:102-103）。
- **hex-helper**：生产实现是隐藏 BrowserWindow 离屏 `executeJavaScript`
  抓 DOM（`scraper-service.js:41-68,83-144`，笨重）；但研究脚本发现了
  **Next.js buildId 直取 JSON** 的干净路子
  （`tools/research/get_full_augments.py:27-33`）；当日缓存 isToday

- **ARAM-tool**：apexlol.info/zh 限速 0.4s 爬取（`apexlol_scraper.py:22,28`）
  存 `apexlol_cache/apexlol_data.json`；**过期预测性后台刷新**：启动加载→
  过期后台静默刷→剩 24h 预刷新→无缓存首用自动爬（`main.py:549-608`）；
  另有 120 条英雄别名表与 mojibake 修复（`apexlol_data.py:16,160`）。

### 3.4 推荐逻辑与防幻觉

- **本项目**：数据直出（OP.GG 锚核心三件 + KB 逐字校验）+ 模型判断

- **ARAM-tool 的防幻觉组合拳与本项目同款收敛**：代码抽出 top-8 统计方案

- 其余两家零推荐逻辑：统计直出排序（PotatoHex `main.py:1202-1235`；

## 4. 他们有、我们没有的功能

- **选人阶段服务**：hex-helper 的队友/板凳英雄按胜率排序
  （`index.js:374-419`）；PotatoHex 读悬停意向 `championPickIntent`，
  选人未锁定即可预览（`hextech_core.py:1859`）。
- **海克斯卡片阶级识别**：棱彩/黄金/白银实抽阶级——本项目
  `augments.json` 有 `is_upgrade` 语义标签但不知道玩家实际抽到的是哪级。
- **极速前瞻**：手动输入英雄名即时出攻略（ARAM-tool `main.py:264-336`），
  适合测试与 API 失效场景。
- **多语言**：ARAM-tool `lang.py` 完整中英双语（STRINGS/PROMPTS，:5-646）。
- **海克斯 API 直读**（见 §1，竞品中仅 ARAM-tool 用了，且只用了一小半）。

## 6. 明确不建议

- **胜率/选取率数字显示**：Riot 政策红线，本项目已正确规避，不回退。
- **PowerShell 调 Windows OCR**：每帧冷启进程开销大、依赖系统语言包，
  本项目 RapidOCR 本地 onnx 更可控。
- **DOM 离屏抓取**（hex-helper 生产路线）：本项目 OP.GG RSC flight 流
  直解更稳；要学就学 buildId 直取 JSON。
- **截图喂多模态替代 OCR**（ARAM-tool v2.5.0 路线）：每次海克斯三选一
  烧 LLM 预算，与"预算守门"冲突；本地 OCR 边际成本为零。
- **Electron 重写 / uiohook·pynput 键盘钩子**：本项目 GetAsyncKeyState
  只读轮询更干净，tkinter 栈已成熟。

## 7. 附录：三家档案要点

**PotatoHex**（B 站作者"柠萌黄叔"/"则暮"）：
依赖仅 5 项（opencv/numpy/Pillow/requests/urllib3），无 LLM SDK；
双进程 launcher.exe（自装依赖+管道回显）→ main.exe，PyInstaller+UPX
打包，release 附缓存 JSON；UI 签名去重防重绘、1.5s/0.4s 双档节流、
DPI 感知。弱点：aramgg.com 改版即失效（靠四级回退硬扛）、powershell
OCR 冷启开销、无配置系统无测试。

**hex-helper**（Crazzies/mooncalf，git@github.com:Crazzies/hex-helper.git）：
Electron portable exe 且 requireAdministrator；uiohook-napi 全局键盘钩子
仅用于 Alt+V 显隐/按住 Ctrl 取消穿透；文档质量好（README/DEVELOPER/
CONTRIBUTING/CHANGELOG）但 v1.0.1 后停更；5584 行一次性 Python 研究爬虫
里藏着 buildId 直取的发现。

**ARAM-tool**（自报 github.com/MJ33520/ARAM-tool，主体由 Google
Antigravity agent 代写，README 贡献者明写 "Antigravity (AI)"）：
四入口（极速前瞻/LCU 全量/海克斯截图/遗留文字），8s 硬超时线程池；
依赖清单有 bug（psutil 实际必需未列、pynput 列了未用）；QUICK_GUIDE_
PROMPTS 定义两次后者覆盖（lang.py:452,521）；缓存 TTL 7 天 + 预测性
刷新是亮点。演化轨迹（OCR→多模态，2026-03-08 起）与本项目思路趋同。

**花絮**：E:\project 里的 `lol-aram-mayhem-hextech-helper` 是本项目前身
参考项目（lcu.py 注释"fork 自参考项目"）。PotatoHex 与 ARAM-tool 同爬
apexlol.info，这一脉社区工具殊途同归（AI 代写 → 砍 OCR 喂多模态 → 或
转向纯统计直显），而真正做"局内动态推荐"的只有本项目。
